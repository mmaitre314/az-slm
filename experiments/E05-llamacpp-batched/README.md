## Question

For offline batch processing, how much does decoding several independent sequences together raise aggregate throughput, and where does it saturate?

## Hypotheses

_Written before the results were known._

- H1: Aggregate decode tok/s rises almost linearly with sequences while memory-bound (weights are read once per step for all sequences), then flattens when compute-bound, around 8–16 sequences, at 15–30 tok/s.
- H2: Per-sequence recurrent state of the 48 Gated DeltaNet layers adds memory traffic that grows with the number of sequences.
- H3: Prefill throughput doesn't change with batching (already compute-bound).

## Setup

- VM `bench-e16v7` (Xeon 6973P-C, Granite Rapids, 8 cores / 16 vCPU, 128 GiB), the same instance as E03. No other benchmark job overlapped (the next one, vLLM setup, started at 07:00; E05 started when the E03 job ended and built `build-native-noamx` first).
- `llama-batched-bench`: N independent sequences, each a 128-token prompt followed by 128 generated tokens; `is_pp_shared` 0 (the shared-prompt mode doesn't work for this hybrid model, E04). `-c 8448 -b 2048 -ub 512 -t 8 -tb 8` (the tool reports `n_kv_max` 16384; its log warns that `n_ctx` is not divisible by `n_seq_max` and rounds it). Prompts are generated by the tool, not natural text, and the generated text was not inspected.
- Each cell (quant, build, N) was run once. Prefill `speed_pp` = N × 128 / `t_pp`, decode `speed_tg` = N × 128 / `t_tg` (aggregate over all sequences).
- The workload differs from the cost model's reference request (512 input tokens): this experiment uses 128-token prompts, see the cost section for how that is handled.

## Method

`bench/llama_batched.sh`: `llama-batched-bench -npp 128 -ntg 128 -npl 1,4,8,16,32 -t 8 -b 2048 -ub 512` on `build-native-noamx` (valid output, E04), plus `build` for Q4_0 and Q8_0 as a speed-only reference (its multi-sequence output is corrupt).

## Analysis

### Orchestrator review and conclusions

- **B6 is closed by E06**: E06 ran `llama-perplexity` on `build-native-noamx` (same commit and flags, on bench-lc2), which
  evaluates 4 sequences per batch by default. Perplexity 6.6 on wikitext-2 and a Q8_0 KL divergence of 0.0006 vs
  BF16 rule out corrupted multi-sequence output on that build. The "valid" rows here stand.
- **The llama.cpp baseline for comparisons is Q4_K_M, 32 sequences, no AMX: $23.9/M tokens blended for 512+128
  on-demand ($4.6/M at Spot)**, with $21.7/M input and $32.8/M output. Even the AMX build at its best (invalid output
  today) would only reach ~$16/M, which bounds what an upstream fix can deliver.
- **Batched decode is compute-bound at ~0.7 TFLOPS**, ~10% of the VNNI peak, so decoding more sequences together
  behaves like a small prefill and saturates at 16–32 sequences. Bigger batches won't fix this; better GEMM
  kernels would, which is the same lever as prefill.
- **Anomalies B2/B3** (decode stalls between 4 and 8 sequences; both builds equal at 4) point to a shared non-GEMM
  cost at small batch, plausibly the per-sequence handling of the 48 recurrent layers (llama.cpp splits ubatches
  per sequence for recurrent memory). Not worth chasing unless llama.cpp ends up the chosen stack.
- **For the cost question, llama.cpp on this VM is uncompetitive**: $24/M tokens on-demand is one to two orders of magnitude above
  hosted API prices for models of this class. Only a large prefill-efficiency gain changes that, which is what E09/E10 test.

### Reporter's analysis (reviewed)

**H1 (decode rises roughly linearly, then flattens at 8–16 sequences and 15–30 tok/s): partly supported on shape, refuted on magnitude.** Aggregate decode on the clean control build goes from 1.97–3.54 tok/s with one sequence to 11.0–14.2 tok/s with 32: 5.35× (Q4_0), 4.02× (Q4_K_M), 5.60× (Q8_0). It is close to linear only up to 4 sequences for Q4_0 and Q8_0 (3.75×, 4.11×; Q4_K_M 2.55× because its single-sequence rate is already high), then stalls (4→8 sequences: +4%, +2%, +22%), jumps at 16 (+34%, +46%, +8%) and is flat from 16 to 32 (+2%, +6%, +3%). So the plateau starts at 16 sequences, and its level (11–14 tok/s) is below the predicted 15–30. The AMX reference reaches 15.3 tok/s (Q8_0, 16 sequences) and 13.3 (Q4_0, 8 sequences, still rising when it crashed).

Why it flattens is compute, not bandwidth: at 32 sequences the Q4_0 step takes 2.45 s, while streaming its 16.3 GB of weights at the ≥86 GB/s that E03 shows is attainable would take 0.19 s (8%). The achieved 0.6–0.8 TFLOPS of aggregate decode is 66–74% of the same build's prefill rate (13.0/18.1, 14.2/21.6, 11.0/14.9 tok/s) and ~10% of the AVX-512 VNNI peak (~7.4 TOPS, assuming two 512-bit ports, 8 cores at 3.6 GHz): decoding 16+ sequences behaves like a small prefill. Even one sequence is not bandwidth-bound on this build: the Q4_0 step takes 0.41 s for 16.3 GB (40 GB/s, half of what E03's AMX build reaches), and steps for 1 to 4 sequences cost about the same (0.41, 0.44 s for Q4_0; 0.51, 0.49 s for Q8_0), which is why 4 sequences is nearly free.

**H2 (recurrent state adds per-sequence memory traffic): the traffic exists but isn't the limiter.** The verbose E03 logs show a 149.62 MiB recurrent-state buffer for one sequence. Reading and writing it once per decode step costs 0.31 GB per sequence, 10 GB per step at 32 sequences, which is 61% of Q4_0's weight bytes (35% of Q8_0's). At 85 GB/s that is ~0.12 s of a 2.25–2.90 s step (4–5%). So traffic grows linearly with sequences as predicted, yet it cannot explain the plateau (derived from buffer sizes, not measured; the assumption is one read and one write of the whole state per step).

**H3 (prefill unchanged by batching): supported.** On the clean control build prefill is 17.8, 18.0, 18.2, 18.1, 18.1 tok/s (Q4_0) from 1 to 32 sequences, 20.7–21.7 (Q4_K_M) and 14.4–14.9 (Q8_0): within 2–5%, and the one-sequence value is the lowest (a 128-token micro-batch under-fills `-ub 512`). On the AMX build it rises 6% (Q4_0) and 14% (Q8_0) from 1 to 4 sequences, then is flat.

**New result: AMX against a clean control.** At matched sequence counts the AMX build prefills 1.9× (Q4_0) and 2.3–2.6× (Q8_0) faster than the native build with AMX compiled out. That is inside E03-H1's 2–4× range, yet E03 saw only 1.3–1.8× at `pp512` against a different no-AMX build (anomaly B4). Even so, 38.6 tok/s for Q8_0 is 2.1 TFLOPS, 3.6% of the 59 TOPS INT8 peak. Decode with AMX is 1.3–2.1× faster at 1, 8 and 16 sequences but 1.0× at 4 sequences (anomaly B3).

**Anomalies / items for investigation**

- B1: the AMX build crashes (SIGSEGV in the AMX Q8_0 tile and VNNI kernels, reading past a buffer) at 16 sequences (Q4_0) and 32 (Q8_0). Independent of the output corruption in E04, it means a batched AMX run is not just wrong but unreliable beyond 8–16 sequences on this commit.
- B2: aggregate decode stalls between 4 and 8 sequences on the clean control build, for all three quants (Q4_0 9.14→9.52, Q4_K_M 9.03→9.20, Q8_0 8.10→9.91 tok/s), with the step time doubling (0.44→0.84 s for Q4_0) and then growing more slowly per added sequence. Cause unknown: a threading or tiling granularity in the CPU matmul or recurrent-state ops is a guess. A profile of decode at 4 and 8 sequences (E07) would show it.
- B3: both builds reach the same decode rate at 4 sequences (Q4_0 9.28 vs 9.14 tok/s, Q8_0 7.95 vs 8.10), although their weight kernels differ and one is 1.5–2× faster at one sequence. That suggests a shared bottleneck at 4 sequences that is not the weight matmul.
- B4: prefill rates here don't match E03's `pp512`: the AMX build gets 35.2 tok/s with four 128-token sequences in one 512-token micro-batch (same `-ub 512` as `pp512`) against 21.1 tok/s for one 512-token prompt in E03 (Q4_0; Q8_0 38.6 vs 22.3). So prefill depends on sequence length or count and not just matrix shape. The no-AMX comparison is muddied by the different build (18.0 here with `build-native-noamx` vs 15.8 with `build-noamx` in E03).
- B5: `build-native-noamx` decodes Q4_0 at 2.44 tok/s with one sequence versus 3.55 for E03's `build-noamx` on the same VM (Q4_K_M and Q8_0 agree within 6%). If the E08 clean control shows the same gap on Q4_0, the repacked Q4_0 kernel differs between the two no-AMX builds (both have 1189 VNNI instructions, so the difference is not simply VNNI code).
- B6: **the multi-sequence output of `build-native-noamx` has never been checked.** E04's sanity script ran `build` and `build-noamx` only, and `build-native-noamx` was compiled at the start of this job (E05 Method calls it "valid output, E04"). Every "valid" row and cost figure in this report depends on it. A `llama-parallel -np 4` comparison against `build-noamx` (a few minutes on one VM) closes this; it was not run here because other jobs share the VM.

## Threats to validity

- One run per cell, one VM instance. The flat prefill rates across N (within 2%) suggest low run-to-run noise on that metric, but decode noise is unknown.
- Prompt length is 128 tokens, not the 512 of the reference workload (see the sensitivity above), and contexts are at most 256 tokens per sequence.
- Output validity of `build-native-noamx` with several sequences wasn't checked for any quant (B6): E04 verified `build-noamx` for Q4_K_M only. The two no-AMX builds contain the same number of VNNI instructions and no AMX code, so a problem is unlikely but unproven.
- The AMX rows are speed references on a build that corrupts and crashes. Corrupt activations can change run time (for example, NaNs), and this was not examined.
- The maximum is 32 sequences, and Q4_K_M was still gaining 6% between 16 and 32. The saturation level may be slightly higher.
- The recurrent-state traffic estimate uses the single-sequence buffer size from E03's logs, assuming it scales per sequence.
- Cost figures inherit the assumption that all N sequences stay in lock step and that 100% utilization is achievable; real batch jobs with ragged lengths will do worse.
